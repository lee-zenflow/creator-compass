# Creator Compass A→B→C 持续优化设计

日期：2026-08-13

## 1. 背景与目标

Creator Compass 已具备可运行的「IP 定位 → 事前创作 → 数据复盘 → 行动任务」闭环、移动端界面、AI 任务、知识入库与运营后台。本轮不重建产品，也不继续横向堆功能，而是依次解决三个已确认的问题：

1. **A：使用路径不够连续。** 用户能找到各功能，但仍需自己判断当前做到哪里、下一步应该做什么，以及失败后如何恢复。
2. **B：视觉反馈仍可深化。** 页面已保持紧凑，但业务模块识别、加载状态、空状态、交互反馈和品牌完整度仍可加强。
3. **C：RAG 可运营性不足。** 知识可以入库、审核和检索，但质量、覆盖、过滤原因和业务引用还不够容易理解。

本轮成功标准不是增加页面数量，而是让用户始终知道当前状态和下一步，让视觉更有层级但不放大模块，并让管理员能判断知识是否可用、为什么命中或没有命中。

## 2. 原则与边界

- 保持原 Figma 的 390×844 紧凑手机造型；同时验收 360×800、390×844、412×915。
- 不使用大面积渐变、大卡片、厚阴影、模板化 Bento 或虚假装饰数据。
- 只从数据库真实状态推导流程，不新增第二套容易漂移的「用户当前阶段」状态机。
- AI 失败必须保留输入、解除业务锁并允许安全重试；不展示虚假阶段、预计时间或自动增长进度。
- RAG 生产检索继续要求来源和切片双重审核、非 Demo、production 范围且已启用。
- 没有真实知识命中时允许基于用户输入生成，但必须明确显示暂无案例依据。
- 不增加新的向量数据库、微服务、图标库或重型动画依赖。
- 每个阶段单独测试、提交、构建和运行；A 稳定后实施 B，B 稳定后实施 C。

## 3. 总体方案

采用三个依次交付的子版本：

| 阶段 | 解决的问题 | 主要交付 |
| --- | --- | --- |
| A 路径闭环 | 用户不知道下一步和失败后怎么继续 | 当前步骤推导、单一主行动、跨模块承接、重试与来源追溯 |
| B 视觉深化 | 状态和模块识别不够丰富 | 业务识别色、统一图标、骨架/空/成功状态、轻动效、品牌与无障碍 |
| C RAG 运营 | 知识质量与召回原因不透明 | 质量概况、来源诊断、检索解释、可读引用、安全重试、真实质量指标 |

三个阶段复用现有 Next.js、PostgreSQL、pg-boss、DeepSeek、MinIO 和 `lucide-react`。除 C 阶段可能增加最小知识质量字段外，A、B 不新增数据库迁移。

## 4. 阶段 A：使用路径与失败恢复

### 4.1 当前步骤推导

新增一个纯服务层 `getNextAction(actor)` 或等价模块。它从现有聚合根读取最少状态并返回一个稳定的展示模型：

```ts
type NextAction = {
  stage: "profile" | "positioning" | "creation" | "task" | "review";
  title: string;
  detail: string;
  href: string;
  actionLabel: string;
  source?: { type: "positioning" | "creation" | "review"; id: string; version: number };
};
```

推导优先级固定为：

1. 没有平台账号和定位记录：完善基础信息或开始定位。
2. 定位访谈未达到可生成条件：继续访谈。
3. 定位 AI run 失败：使用已保存内容重试。
4. 定位报告待确认：选择定位方向。
5. 定位已确认、没有创作项目：开始首次创作。
6. 创作 AI run 失败：从已保存需求重试。
7. 方案已生成、任务尚未写入：预览并写入任务。
8. 存在未完成高优先级任务：继续执行任务。
9. 有已发布内容但没有对应复盘：开始数据复盘。
10. 复盘完成并生成行动任务：执行改进任务。
11. 没有更紧迫状态：开始下一轮创作。

同一时间只显示一个最重要主行动。推导函数不写数据库，避免页面展示和业务数据成为两套真值。

### 4.2 工作台与跨模块衔接

- 工作台在账号信息下方增加 64–72px 的「当前步骤」行，包含小图标、阶段、说明和一个动作入口。
- 原「接下来」仍最多展示两条任务，避免和当前步骤重复；当前步骤指向任务时，列表过滤掉同一任务或改为显示第二、第三优先事项。
- 定位确认页的下一步固定为任务预览；任务写入成功后提供「开始首次创作」。
- 创作方案页的下一步固定为任务预览；任务写入成功后返回任务中心或开始执行第一条任务。
- 复盘报告页的下一步固定为行动任务；写入后返回任务中心，并保留报告入口。
- 任务详情显示来源模块、来源报告标题、版本和「为什么做」，用户可返回生成该任务的真实报告。
- 所有流程页都保留明确返回路径，不通过浏览器历史猜测上一页。

### 4.3 失败恢复

统一恢复模型，服务端返回固定错误类型，页面展示安全文案和可执行动作：

| 错误 | 页面动作 | 后端要求 |
| --- | --- | --- |
| `NOT_CONFIGURED` | 提示配置后重试 | 不创建假 AI run 或结果 |
| `TIMEOUT` | 使用原输入重试 | 新建合法 attempt 或重新排队失败 run |
| `RATE_LIMITED` | 稍后重试 | 保留业务输入并解除 processing 锁 |
| `AI_INPUT_CHANGED` | 使用最新内容重新生成 | 不把旧 input hash 的结果写入报告 |
| 结构校验失败 | 重试生成 | 保留安全错误码，不输出模型原文 |
| 网络/队列临时失败 | 重试提交 | 事务失败不消耗游客配额、不留下假 processing |

重试必须幂等：同一恢复操作重复点击返回同一活动 run；内容发生变化时明确创建新请求或返回冲突，不能把失败 run 冒充 processing。

### 4.4 A 阶段组件边界

- `NextActionService`：读取真实状态并推导一个主行动。
- `CurrentStepRow`：只负责紧凑展示，不做业务判断。
- `RecoveryAction`：将安全错误码映射为说明和 server action。
- 现有定位、创作、复盘和任务服务继续拥有写入职责。

每个单元可独立测试；UI 组件不直接查询数据库，推导服务不渲染文案以外的 JSX。

## 5. 阶段 B：视觉深化

### 5.1 业务识别系统

沿用低饱和青绿色主色，并为业务模块增加弱识别色：

- 定位：浅青绿色，表示方向与确认。
- 创作：雾蓝色，表示方案与编辑。
- 复盘：浅沙金色，表示判断与复查。
- 任务：中性灰青色，来源小标记继承上游模块颜色。
- 错误：低饱和红，只用于失败和危险操作。

识别色只用于 32px 图标底座、1–2px 状态边和小标签，不铺满整张卡片。

### 5.2 页面层级与组件

- 图标统一 18px、`strokeWidth=1.8`；每个一级模块、报告类型、任务来源和后台菜单均有文字配套图标。
- 工作台的当前步骤、周期指标、趋势、任务和最近报告通过间距与分隔线分层，不额外堆叠大卡片。
- 候选卡保持约 148px，任务卡保持约 84px；列表文本最多两行，完整内容进入详情页。
- 新增与真实布局匹配的骨架组件：指标条、三行列表、候选卡、任务卡；不使用覆盖全屏的通用转圈。
- 空状态由 24px 图标、短标题、一句解释和一个行动组成；没有行动价值的空状态只显示说明。
- 成功操作使用页面内状态行或短暂反馈，不弹阻断式模态框。
- 按钮、列表入口和底部导航增加 160–220ms 的颜色、透明度和 1px 位移反馈。
- `prefers-reduced-motion: reduce` 时关闭非必要动效。

### 5.3 品牌与无障碍

- 增加统一 favicon、应用图标和必要的 metadata，不引入营销型大图。
- 增加跳至正文入口、清晰的键盘焦点、表单错误关联和有意义的 aria label。
- 增加品牌化 404 页面，提供返回工作台和工具箱两个真实入口。
- 桌面宽屏继续只把 390px 手机画板居中，不横向拉伸用户产品；后台保持独立桌面布局。

## 6. 阶段 C：RAG 质量与可解释运营

### 6.1 知识概况

后台知识首页使用真实数据库聚合展示：

- 来源总数、待处理、待审核、生产可用、停用和失败数量。
- 切片总数、已审核生产切片和需要修复的切片数量。
- 最近入库失败任务及固定安全错误码。
- 按平台与内容类型的来源覆盖；样本不足时只显示数量，不做质量结论。
- 真实检索记录累计到最低样本后再显示命中率和无命中趋势。

### 6.2 来源与切片质量诊断

质量检查应尽量在查询时计算，只有需要稳定索引或历史追踪时才增加字段：

- 正文字符数、切片数、平均切片长度。
- 过短、过长、空白或高度重复切片。
- 缺少标题、平台、内容类型、关键词或摘要。
- 来源审核状态、切片审核进度和最近审核记录。
- 内容哈希重复但授权或来源不同的记录只提示，不自动合并。

质量提示不等同审核结论。AI 可以提出标签和摘要候选，但不能批准来源、切片或平台规则。

### 6.3 检索解释

检索服务保留现有生产闸门和最终排名，同时返回仅供管理员查看的解释模型：

```ts
type RetrievalExplanation = {
  itemId: string;
  sourceId: string;
  finalScore: number;
  signals: {
    exactTag: number;
    substring: number;
    trigram: number;
    fullText: number;
    recencyOrWeight: number;
  };
  acceptedReasons: string[];
  filteredReason?: "source_unapproved" | "item_unapproved" | "disabled" | "demo" | "scope" | "platform" | "content_type";
};
```

- 业务生成仍只接收最终可信片段，不接收管理员调试信息。
- 检索实验室展示前 8 条命中、各信号贡献、排序原因和过滤统计。
- 同一来源最多占 3 条；其余高分结果用于补足来源多样性。
- 解释分数只用于相对比较，不包装成「准确率」或用户成功概率。

### 6.4 用户可读引用

- 定位、创作和复盘详情将引用 ID 转换为资料标题、来源类型、短摘要和审核属性。
- 用户只看到本次 retrieval snapshot 中实际引用的资料，不可通过 URL 参数读取其他用户或其他 run 的来源。
- 没有引用时统一显示「仅基于本次输入，暂无匹配案例依据」。
- 内部示例和 development-only 资料不出现在用户引用中。

### 6.5 入库失败与重试

- 临时错误：网络超时、对象存储故障、数据库暂时失败，可从后台重试。
- 永久错误：不支持的格式、SSRF 拒绝、文件超限、DOCX 不安全、解析后正文为空，提示重新提交或改用手动文本。
- 重试沿用同一来源和新任务记录，不覆盖审核历史，也不把失败任务改写为成功历史。
- 后台和日志只展示固定错误码与安全说明，不展示内部 IP、签名 URL、API 密钥、完整用户输入或模型原始失败正文。

## 7. 数据流

### 7.1 用户闭环

```text
真实业务状态 → NextActionService → 工作台当前步骤
    ↓ 用户进入对应模块
定位/创作/复盘服务 → 报告版本 → 任务版本与来源快照
    ↓
任务完成或内容发布 → 下一次当前步骤重新推导
```

### 7.2 RAG 运营

```text
URL/文件/文本 → 安全校验 → 私有归档 → 解析 → 切片 → AI 候选标签
    ↓
来源人工审核 + 切片人工审核 → production gate
    ↓
受控查询 → 混合检索 → 来源多样性 → retrieval snapshot
    ↓
DeepSeek 生成 → 引用 pair 校验 → 报告可读引用
```

## 8. 测试与验收

### 8.1 A 阶段

- 表驱动测试覆盖全部下一步优先级，证明同一状态只返回一个主行动。
- 定位、创作、复盘的超时、限流、输入变化和重复重试均可恢复且幂等。
- 报告到任务、任务到复盘的链接使用真实业务 ID 和版本，不产生死链。
- Playwright 覆盖新用户、处理中、失败恢复、已有任务和复盘后下一轮五类状态。

### 8.2 B 阶段

- 360×800、390×844、412×915 无横向溢出、底栏遮挡和列表大卡。
- 候选卡、任务卡和当前步骤高度有上限，长 AI 内容不会撑破列表。
- 键盘焦点、跳至正文、减少动态偏好、404 和主要空状态通过组件或 E2E 验证。
- 浏览器控制台无前端错误；关键页面保留截图证据。

### 8.3 C 阶段

- 待审核、拒绝、停用、Demo、development-only 或平台不匹配资料永不进入业务检索。
- 固定回归查询召回预期切片，且单来源不超过 3 条。
- 检索解释的信号之和与最终排序逻辑一致；业务生成路径不暴露调试字段。
- 引用必须属于同一 run 的 retrieval snapshot；无命中页面展示真实无依据文案。
- URL、PDF、DOCX、TXT、手动文本的成功与安全失败路径均有回归测试。

### 8.4 最终发布门槛

- 全量单元与真实 PostgreSQL 集成测试通过。
- 完整游客 → 定位 → 创作 → 复盘 → 任务 → 注册合并 E2E 通过。
- ESLint、TypeScript、Next.js 生产构建、worker 构建和迁移检查通过。
- Web、数据库、worker、私有存储健康检查为 healthy。
- 变更中不存在 API 密钥、私有 URL、测试缓存或伪造生产数据。

## 9. 分阶段提交与回滚

- A、B、C 各自独立提交；每个提交都能运行，不把未完成的下一阶段代码混入前一阶段。
- A 只增加推导与恢复，不修改视觉系统的大范围令牌。
- B 只使用 A 已稳定的展示模型，不改变业务真值和幂等规则。
- C 不修改用户闭环状态推导，只增强知识运营与引用展示。
- 任一阶段出现回归时可回退该阶段代码，不回滚数据库历史；C 若新增迁移必须向前兼容。

## 10. 本轮不做

- 支付、套餐、订单、会员权益。
- 第三方平台 OAuth、自动发布和未经授权的数据抓取。
- 新向量数据库、独立检索微服务或多模型路由平台。
- 社区、排行榜、模板市场和泛内容生成工具。
- 把内部示例、估算指标或人工辅助结果写成真实用户成功案例。

## 11. 完成定义

用户打开工作台时能在一个紧凑模块内理解当前阶段，并一键进入最重要的下一步；AI 失败后可以从已保存输入恢复，不会卡在假处理中。视觉在三个手机尺寸下保持原 Figma 密度，同时具备清晰模块识别、加载、空、成功、错误和无障碍状态。管理员可以判断知识是否可用、为什么命中或被过滤，用户可以阅读真实引用；没有知识命中时产品明确承认无案例依据。
